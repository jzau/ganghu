# Shared payment service: fixes needed for chatbot integration

Reviewed source: `/Users/jie/Desktop/BEAMAN/web3/callcoin-web/payment-service` on 2026-09-07. This document describes changes for that service's owner; this task does not modify or deploy the shared service. Findings below come from the implementation, not assumptions in its API guides.

These issues may be deferred for the current POC. The chatbot limits the immediate risk by using server-owned prices, re-querying payment state, matching IDs/provider/amount/currency, and applying tokens once in a database transaction. Those controls do not make the shared service production-ready: complete the applicable P0 items before accepting production payments.

## Production launch blockers

| Priority | Source | Finding | Required change and acceptance check |
| --- | --- | --- | --- |
| P0 | `middleware/service-auth.js` | Requests are accepted when `INTERNAL_AUTH_SECRET` is absent. The actual request header is `X-Internal-Auth`, despite older documentation describing Bearer auth. | Fail startup or reject requests when the secret is missing. Use constant-time comparison and restrict API access to trusted applications. Missing, wrong and empty credentials must never create or read a payment. |
| P0 | `controllers/webhook-controller.js` — PayPal | Missing `PAYPAL_WEBHOOK_ID` or disabled verification bypasses signature checks. | Fail closed in production, require webhook ID and verification, and reject tampered or unsigned payloads. Tests must show forged capture notifications cannot set `captured`. |
| P0 | `controllers/webhook-controller.js` — PayPal approval | After capture API returns, the code sets `captured` without checking the actual capture status. Polling consumers can see it before the completed event. | Set `captured` only for verified `COMPLETED` captures whose merchant, order, currency and amount match. Pending, declined and malformed capture responses must remain unpaid. Query refresh must preserve those distinctions. |
| P0 | `controllers/webhook-controller.js` — OmiPay | `return_code === 'SUCCESS'` can classify a notification as paid even with a conflicting refund/closed trade state. `services/providers/omipay.js` signs merchant/time/nonce, not the order fields. | Confirm the current OmiPay notification contract. Treat the callback as a signal and query the provider for authoritative order state and charged amount/currency. Give refund/closed states proper precedence; apply replay protection and constant-time verification. A reused signature with changed order fields must not credit another order. |
| P0 | `services/payment-service.js`, `services/idempotency-service.js` | Gateway creation happens before the idempotency lookup. The lookup/insert also does not reserve the key atomically; multiple-provider creation ignores the key. | Reserve the request key and request hash atomically before any provider side effect; forward a stable provider idempotency key or merchant order number. Persist an order intent before calling the gateway. Test simultaneous same-key requests, changed-body conflicts, timeouts and crashes between gateway creation and persistence. There must be one provider order per logical attempt. |
| P0 for non-USD offers | `services/providers/omipay-provider.js`, `services/providers/omipay.js` | The adapter ignores the requested currency and always converts input from USD to CNY, with a default 1% rate buffer. Response currency/amount describe the request, not the CNY charge. | Either explicitly reject non-USD input (the chatbot currently enforces this) or implement currency-aware conversion. Expose source amount/currency, charged amount/currency, rate, buffer and quote expiry; use deterministic minor-unit rounding. CNY input must not be converted as USD. |
| P0 for PayPal | `services/providers/paypal-client.js` — `createOrder` | Supplied `returnUrl` and `cancelUrl` are ignored; both are hardcoded to `satoshh.cc`. | Honor validated caller URLs, with an application-specific origin allowlist. Confirm sandbox approval and cancellation return to the chatbot, without granting credit based on a browser redirect. |

## Reliability and extensibility work

| Priority | Source | Required change and acceptance check |
| --- | --- | --- |
| P1 | `services/outbound-webhook-client.js`, callback dispatch in `controllers/webhook-controller.js` and `services/payment-service.js` | Persist callback events in an outbox with a stable event ID, retry/backoff, delivery state and dead-letter handling. Errors are currently logged and swallowed, and several paths notify only on a status transition. A temporary chatbot outage must not lose capture or refund notifications. Do not block a read/query response while synchronously awaiting its callback: the chatbot callback re-queries the payment. |
| P1 | Per-order callbacks and auth | Validate callback destinations per authenticated application to prevent requests to arbitrary/private hosts. Use per-application callback credentials or HMAC with timestamp/event ID. Currently all custom callbacks use the shared `CORE_SERVICE_API_KEY`. Preserve existing applications during credential migration. |
| P1 | `services/payment-service.js` — `getPayment` | Expose freshness and explicit verification failures. OmiPay query errors currently return the last saved state; PayPal reads return stored state without refreshing at the provider. Add authenticated lookup by application + merchant `orderId` for recovery after a timed-out create response. |
| P1 | Refund handling | PayPal refund handling looks up a capture using `resource.id`, which identifies the refund in a refund event; verify and use the associated capture ID. Persist refund ID, refunded minor units/currency, cumulative refunded amount, full/partial status and original payment link. Handle duplicates and out-of-order capture/refund events. The chatbot currently flags credited refunds for manual review and does not guess a token debit. |
| P1 | Payment states | Make transitions monotonic and event-deduplicated; capture must not overwrite an established refund. Bind every provider response/event to provider order, merchant, amount and currency before changing status. |
| P1 before crypto enablement | `services/providers/crypto-provider.js`, crypto webhook handler | Define chain/token/address/amount display and expiry semantics, verify paid amount/currency, add query-based reconciliation, and test webhook URL construction (`PAYMENT_SERVICE_PUBLIC_URL` is concatenated with `/webhooks/crypto`). The chatbot intentionally exposes hosted PayPal/OmiPay checkouts only in this version. |
| P2 | Provider capability catalog | Add an authenticated capabilities endpoint describing enabled providers, actual methods, supported currencies, checkout type, refund support and environment. The chatbot currently uses a server-configured method catalog. OmiPay is one hosted checkout; its API does not accept distinct WeChat/Alipay method selection. |
| P2 | `services/providers/cash-provider.js` | Keep cash out of online recharge until a separate authenticated, audited settlement workflow exists. The current adapter creates a reference but does not verify payment. |

## Contract the chatbot currently uses

- `POST /api/payments`, with `X-Internal-Auth` and `Idempotency-Key: chatbot:<localOrderId>`.
- Body: `orderId`, server-calculated `amount`, `currency`, **one** `providers` entry, `metadata`, `returnUrl`, `cancelUrl`, `callbackUrl`, `refundCallbackUrl`.
- `GET /api/payments/:paymentId` with `X-Internal-Auth`.
- Single-payment response: `id`, `orderId`, `status`, numeric `amount`, `currency`, `provider`, HTTPS `approvalUrl`. `captured` must mean verified, completed payment, not approval or pending capture.
- Both callbacks target the chatbot's `POST /api/payments/callback`. Send `Authorization: Bearer <CORE_SERVICE_API_KEY>` plus `orderId` and `paymentId`. Other callback fields are treated as hints; the chatbot re-queries the service and compares the saved amount, currency, provider and IDs.
- A provider-specific order number alone is not the payment service's `id`.

Keep this contract backward compatible when fixing the service. If response money types, statuses or authentication change, version the API and update the chatbot adapter and contract tests together.

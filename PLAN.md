# GANGHU AI 工夫 V1 Plan

## Product Summary

Build a simple AI chat application similar to an early ChatGPT experience.

Users log in with phone number and OTP, redeem app tokens using codes generated by an admin, choose an available LLM model, and chat with streamed responses. Admins can manage available models, generate redeem codes, view users and balances, and manually adjust balances.

This is a v1 product, so the architecture should stay simple and avoid unnecessary services.

## Confirmed Requirements

### User App

- Users log in with phone number and OTP.
- OTP sending and verification are handled by an external auth service.
- The auth service API will be provided later.
- Users have an app token balance.
- Users can redeem app tokens using a string code.
- Users can chat only when they have enough app tokens.
- Users can choose from enabled LLM models.
- Users can switch models.
- Chat responses should stream like ChatGPT.
- Users can see conversation history.
- Users can soft-delete conversations from history.

### Admin Dashboard

- Admin dashboard is protected by a single password.
- No admin username is required for v1.
- Admin can configure available LLM models.
- Admin can generate redeem codes.
- Redeem codes are single-use by default.
- Redeem codes can optionally have a usage limit.
- Redeem codes can optionally be unlimited-use.
- Admin can view users and balances.
- Admin cannot view user chat history in v1.
- Admin can manually adjust a user balance.
- Admin audit log can be skipped for v1.

### LLM Providers

- Use OpenRouter for v1.
- Initial models:
  - DeepSeek
  - Kimi

### Deployment

- Deploy to a Debian VPS.
- Do not use Docker for v1 unless needed later.
- Use Nginx as reverse proxy.
- Run the Node.js backend with PM2 or systemd.
- Serve the built React app as static files.
- Use PostgreSQL on the server.

## Terminology

Use **app tokens** for the product balance system.

Do not call them credits in the UI or API unless a later product decision changes this.

App tokens are separate from provider LLM tokens, but pricing should feel similar to actual LLM token usage.

Example:

```txt
deepseek-chat:
1000 app tokens / 1000 input LLM tokens
2000 app tokens / 1000 output LLM tokens
```

## Framework Decision

Use **Fastify + TypeScript** for the backend.

Reasoning:

- Simpler than NestJS for v1.
- More structured and TypeScript-friendly than plain Express.
- Good validation and plugin patterns.
- Good logging integration through Pino.
- Suitable for streaming endpoints.

NestJS can be reconsidered later if the backend becomes much larger or requires heavier application structure.

## Database Decision

Use **PostgreSQL + Prisma**.

Reasoning:

- Strong transactional guarantees.
- Good fit for balances, ledgers, redeem codes, model configs, conversations, and messages.
- Prisma gives fast development and readable migrations.

## App Token Deduction

OpenRouter responses follow an OpenAI-like shape and can provide usage data:

- `prompt_tokens`
- `completion_tokens`
- `total_tokens`
- optional cost / generation stats

For streaming, usage is received at the end of the stream, or can be queried afterward from OpenRouter generation stats.

V1 deduction should be based on actual input/output usage:

```txt
deducted_app_tokens =
  ceil(prompt_tokens / 1000 * input_app_tokens_per_1k)
  + ceil(completion_tokens / 1000 * output_app_tokens_per_1k)
```

Each model should have separate input and output app token pricing because providers often charge different rates for input and output tokens.

The backend should also store OpenRouter actual cost when available, but user-facing charges should come from admin-configured app token pricing.

## Balance Behavior

Do not allow users to start chat if they do not meet the selected model's minimum required balance.

For v1:

- Allow an in-progress request to finish.
- Deduct actual app tokens after usage is known.
- If the final charge exceeds the user's balance, set balance to `0`.
- Do not allow negative balances.
- Block future chats until the user redeems or receives more app tokens.

This avoids interrupting streamed responses while keeping the balance model simple.

## Context Window Handling

Store `context_window_tokens` per model.

The context window includes:

```txt
system prompt
conversation history sent to the provider
latest user message
model output
```

Simple v1 behavior:

- Load recent conversation messages.
- Keep only the messages that fit within the model context limit.
- Skip oldest messages when the conversation is too long.
- Do not implement summarization in v1.

## Redeem Code Behavior

Redeem codes should support:

```txt
code
app_token_amount
usage_limit
used_count
expires_at
enabled
created_at
```

Usage limit behavior:

- Single-use by default: `usage_limit = 1`
- Limited multi-use: `usage_limit = N`
- Unlimited: `usage_limit = null`

Redemption must be transactional:

1. Validate code exists.
2. Validate code is enabled.
3. Validate not expired.
4. Validate usage limit is not exceeded.
5. Validate user has not already used it if required by product rule.
6. Create redemption record.
7. Increase user balance.
8. Create app token ledger entry.
9. Increment code usage count.

## Conversation Deletion

Use soft delete for v1:


Users do not see soft-deleted conversations.

Admin cannot view user chat history in v1.

## Chat Request Flow

1. User submits a message with conversation ID and model ID.
2. Backend authenticates user.
3. Backend loads selected model config.
4. Backend checks model is enabled.
5. Backend checks user balance is at least `minimum_required_balance`.
6. Backend stores the user message.
7. Backend loads conversation history.
8. Backend trims history to fit `context_window_tokens`.
9. Backend calls OpenRouter with streaming enabled.
10. Backend streams tokens/events to the frontend through SSE.
11. Backend stores assistant response.
12. Backend reads usage from final stream chunk or generation stats.
13. Backend calculates app tokens charged.
14. Backend deducts from user balance, clamping to zero if needed.
15. Backend creates usage record and ledger entry.
16. Backend sends final stream event with updated balance and usage.
